## 1. 项目定位

### 1.1 项目是做什么的？

Medical RAG 是一个**基于 LangChain + LangGraph + Milvus 的医疗领域智能问答系统**，采用检索增强生成（RAG）架构，支持多向量混合检索和 Agent 智能体自主决策。

### 1.2 解决了什么业务问题？

- **医疗知识检索效率低**：传统关键词检索无法理解语义，本项目通过稠密+稀疏混合向量检索精准定位医学知识。
- **医学问答专业性不足**：通用 LLM 在医疗领域容易产生幻觉，通过 RAG 约束生成内容基于权威医学知识库。
- **多轮对话上下文丢失**：支持多轮问讯，在连续对话中保持上下文一致性。
- **领域迁移成本高**：采用约定数据格式，可无缝迁移到法学、金融等其他垂直领域。

### 1.3 目标用户是谁？

- 医疗机构的智能导诊、预问诊系统开发者
- 医学知识库的运维与问答系统构建者
- 需要将 RAG 能力迁移到其他垂直领域的 AI 应用开发者

### 1.4 属于哪一类 Agent？

**工作流 Agent（Workflow Agent）+ 检索 Agent（RAG Agent）的混合体**。

系统将检索决策权完全交给 Agent 托管：Agent 自主判断是否需要检索、检索什么内容、用何参数，以及是否开启网络检索来补充知识。这使其超越了静态 RAG 流水线，具备了 Agent 的自主决策能力。

### 1.5 为什么需要用 Agent，而不是普通应用？

| 能力     | 普通 RAG 应用 | 本项目 Agent               |
| :------- | :------------ | :------------------------- |
| 检索触发 | 固定触发      | Agent 自主判断是否需要检索 |
| 检索参数 | 硬编码        | Agent 动态决定检索策略     |
| 答案验证 | 直接返回      | Agent 判断是否符合文档事实 |
| 知识补充 | 不支持        | Agent 决定是否开启网络检索 |
| 多轮对话 | 简单拼接      | Agent 管理上下文与记忆     |

普通 RAG 应用是"固定流水线"，而本项目让 LLM 作为"大脑"自主决策整个检索与生成流程。

## 2. 业务流程

### 2.1 用户输入什么？

用户输入**自然语言医学问题**，支持单轮问答和多轮对话两种模式。

### 2.2 系统输出什么？

系统输出**基于医学知识库的准确回答**，附带检索来源和置信度信息。

### 2.3 完整流程示例

**用户问题**："高血压患者可以服用布洛芬吗？"

| 步骤 | 做了什么                       | 目的                                                      | 涉及模块                                 |
| :--- | :----------------------------- | :-------------------------------------------------------- | :--------------------------------------- |
| 1    | 用户输入问题                   | 发起问答请求                                              | WebUI / API                              |
| 2    | Agent 解析用户意图             | 理解问题类型、识别关键实体（高血压、布洛芬）              | `MedicalAgent.py`                        |
| 3    | Agent 决策：是否需要检索？     | 判断问题是否需要外部知识支撑                              | `SearchGraph.py`                         |
| 4    | 执行混合检索                   | 稠密向量（语义相似）+ 稀疏向量（BM25 关键词匹配）并行检索 | `HybridRetriever.py`、`KnowledgeBase.py` |
| 5    | 检索结果重排与整合             | 合并多路召回结果，去重排序                                | `HybridRetriever.py`                     |
| 6    | Agent 判断检索结果是否符合事实 | 验证检索内容与问题的相关性                                | `MedicalAgent.py`                        |
| 7    | Agent 决策：是否需要网络检索？ | 若知识库覆盖不足，开启腾讯云网络搜索补充                  | `TencentSearch.py`                       |
| 8    | LLM 基于检索结果生成回答       | 约束生成，避免幻觉                                        | `SimpleRag.py` / `MultiDialogueRag.py`   |
| 9    | 返回最终答案给用户             | 完成问答闭环                                              | WebUI / API                              |

### 2.4 多轮对话增强流程

对于多轮对话场景，系统额外执行：

- **Token 估计**：控制上下文窗口长度
- **摘要提取**：对历史对话进行压缩
- **检索文档动态整合**：根据当前问题动态调整检索策略

```

```



## 4. Agent 核心设计

### 4.1 Agent 的角色是什么？

Agent 扮演**"智能检索管家"**的角色—— 不直接回答问题，而是全权托管检索决策流程，包括"要不要搜、怎么搜、搜得对不对、要不要补充搜"。

### 4.2 Agent 如何理解用户任务？

通过 LangChain 的 LLM 调用 + 提示词模板（`prompts/templates.py`），将用户问题解析为结构化的检索任务。

### 4.3 Agent 是否会进行任务拆解或规划？

**会**。通过 LangGraph 构建的状态机实现任务规划：

- `SearchGraph.py` 实现单轮对话的检索图
- `MedicalAgent.py` 实现多轮问讯的复杂决策图

### 4.4 Agent 如何决定是否调用工具？

Agent 基于 LLM 推理自主决策：

1. **是否需要检索**：判断问题是否超出自身知识或需要精确事实支撑
2. **检索参数**：动态决定检索的 top_k、阈值等
3. **是否开启网络检索**：当知识库覆盖不足时，调用 `TencentSearch.py`

### 4.5 项目中有哪些 Tools？

| 工具         | 位置               | 功能                              |
| :----------- | :----------------- | :-------------------------------- |
| 混合检索工具 | `AgentTools.py`    | 调用 Milvus 执行稠密+稀疏混合检索 |
| 网络搜索工具 | `TencentSearch.py` | 腾讯云网络检索，补充外部知识      |
| 答案验证工具 | `AgentTools.py`    | 判断检索结果是否符合文档事实      |

### 4.6 是否使用 RAG、MCP 或 Skills？

| 能力       | 是否使用 | 说明                                          |
| :--------- | :------- | :-------------------------------------------- |
| **RAG**    | ✅        | 核心能力，多向量混合检索                      |
| **MCP**    | ❌        | 未使用                                        |
| **Skills** | ⚠️        | 工具调用机制类似 Skill，但未明确命名为 Skills |

### 4.7 Agent 如何生成最终结果？

1. Agent 收集检索结果（知识库 + 可能的网络搜索结果）
2. 将检索文档作为上下文注入 LLM
3. LLM 基于检索内容生成回答（`SimpleRag.py` / `MultiDialogueRag.py`）
4. 可选：Agent 再次验证回答是否符合文档事实

### 4.8 是否支持多轮对话、记忆或上下文管理？

**全支持**：

- **多轮对话**：`MultiDialogueRag.py`
- **记忆管理**：通过 LangChain 的对话记忆机制
- **上下文管理**：Token 估计 + 摘要提取 + 检索文档动态整合

## 6. 总结与学习价值

### 6.1 核心亮点

1. **Agent 化的 RAG**：将检索决策权完全交给 Agent 托管，实现"智能检索管家"
2. **多向量混合检索**：稠密向量（语义）+ 稀疏向量（BM25 关键词）双路召回
3. **领域迁移能力**：约定数据格式，可无缝迁移到法学、金融等领域
4. **完整的工程化设计**：从数据预处理、入库、检索、问答到评测的端到端方案
5. **多轮对话增强**：Token 估计、摘要提取、文档动态整合

### 6.2 不足

1. 缺少容器化部署方案（Docker/K8s）
2. 缺少用户认证与权限控制
3. 工具扩展需要修改核心代码，缺乏插件化设计
4. 未见明确的 RAG 未命中降级策略

### 6.3 值得学习的设计

1. **Agent 与 RAG 的融合模式**：让 Agent 托管检索决策，而非固定流水线
2. **混合检索架构**：稠密+稀疏向量的双路召回与重排
3. **配置驱动的领域迁移**：通过 YAML 配置切换模型和领域词表
4. **多轮对话的状态管理**：Token 估计 + 摘要提取的上下文压缩策略
5. **LangGraph 的状态机编排**：用图结构管理 Agent 决策流程

### 6.4 不适合直接照搬的设计

1. **医疗领域的专用词表**：领域词表需要根据具体业务重新构建
2. **腾讯云搜索工具**：网络搜索需要替换为业务实际的搜索服务
3. **数据格式约定**：需要根据业务数据结构调整入库流水线

### 6.5 二次开发优先改进项

1. **增加容器化部署**：编写 Dockerfile 和 docker-compose.yml
2. **完善 API 鉴权**：增加 API Key 认证和用户管理
3. **工具插件化**：设计工具注册机制，新工具通过配置注册
4. **增加 RAG 未命中降级**：实现"知识库不足→网络搜索→人工兜底"的降级链路
5. **补充监控指标**：接入 Prometheus，增加检索延迟、命中率等业务指标

### 6.6 面试表达

> **项目背景**：Medical RAG 是一个基于 LangChain 和 LangGraph 的医疗领域智能问答系统，解决传统医疗问答中检索精度不足和 LLM 幻觉问题。项目支持一键部署和跨领域迁移。
>
> **技术架构**：采用 LangChain 0.3.27 + LangGraph 0.6.6 构建 Agent 框架，Milvus 2.6.x 作为向量数据库支持稠密+稀疏混合检索，集成 LangSmith 实现可观测性，支持 OpenAI 和 Ollama 等多种 LLM 提供商切换。
>
> **Agent 工作流**：用户提问后，Agent 首先通过 LLM 推理判断是否需要检索以及检索策略，然后调用混合检索工具从 Milvus 召回相关文档，再判断检索结果是否符合事实，若知识覆盖不足则自动开启网络搜索补充，最后基于检索内容生成回答并返回用户。整个流程通过 LangGraph 状态机编排，实现了检索决策的完全 Agent 化。
>
> **Tools / RAG 使用情况**：系统核心 Tools 包括混合检索工具（稠密+稀疏向量）和腾讯云网络搜索工具。RAG 采用多向量混合检索策略，通过 HybridRetriever 并行执行语义检索和 BM25 关键词检索，再将多路结果整合重排。多轮对话场景下，系统通过 Token 估计和摘要提取实现上下文压缩管理。
>
> **项目亮点**：一是将 Agent 与 RAG 深度融合，让 Agent 全权托管检索决策；二是多向量混合检索显著提升医学问答的召回精度；三是配置驱动的架构设计支持快速迁移到法学、金融等其他垂直领域；四是端到端的数据流水线覆盖从预处理到评测的完整链路。
>
> **企业级落地思考**：当前项目在工程化方面已有较好基础，但要真正落地企业生产环境，还需要补充容器化部署方案、API 鉴权与用户权限管理、工具调用的插件化扩展机制、RAG 未命中的降级策略，以及接入 Prometheus 等监控体系来保障系统的稳定性和可观测性。
