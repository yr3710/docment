## 1. 项目定位

### 1.1 项目是做什么的？

ConstructDrawingAI 是一个**将二维工程图纸（建筑施工图、电气图、P&ID 工艺流程图等）转化为结构化、可决策数据的 AI 系统**。它通过五层架构（L0 数据接入、L1 感知检测、L2 语义映射、L3 算量引擎、L4 Agent 问答）将图纸中的符号、组件、连接关系提取出来，生成带有置信度和证据链的量化数据。

### 1.2 解决了什么业务问题？

在建筑、工程和施工行业，图纸理解长期依赖人工——造价师需要手动数图纸上的插座数量，工程师需要逐页追踪管线连接，项目经理需要反复翻阅图纸回答"这个房间有多少个消防喷头"之类的问题。这个过程耗时、易错，且知识沉淀困难。

ConstructDrawingAI 解决的核心问题是：**将非结构化的图纸图像，转化为可查询、可审计、可决策的结构化数据**，让"图纸问答"从人工翻阅变成数据库查询。

### 1.3 目标用户是谁？

- **工程造价师/估算员**：自动进行工程量统计（设备数量、管线长度、面积等）
- **建筑/电气/工艺工程师**：快速查询图纸中的组件信息和连接关系
- **项目经理**：通过自然语言问答获取图纸洞察，生成 RFI（信息请求）草稿
- **EPC 总包企业**：将图纸数据化后接入企业 BIM 工作流

### 1.4 属于哪一类 Agent？

**数据分析 Agent + 工作流 Agent 的混合体**。

它不同于客服 Agent（对话为主）或代码 Agent（代码生成），而是**以结构化数据为中心的决策支持 Agent**。具体来说：

- L0-L3 是典型的**工作流 Agent**（数据处理流水线）
- L4 是**数据分析 Agent**（基于结构化数据的 Q&A）

### 1.5 为什么需要用 Agent，而不是普通应用？

普通应用只能做固定规则的处理（如 OCR 识别文字）。而这里需要：

1. **视觉理解**：识别图纸上成千上万种符号（不同项目、不同标准的图例各不相同）
2. **语义映射**：将检测到的符号映射到 IFC 类、MasterFormat 编码等行业标准
3. **自然语言交互**：用户问"E-201 上有多少个断路器？"，系统需要理解意图并查询结构化数据
4. **证据追溯**：每个答案都要能追溯到具体图纸和实体，满足工程行业的审计要求

这些能力需要**计算机视觉模型 + 规则引擎 + LLM 的组合**，而非单一应用能完成。

## 2. 业务流程

### 用户输入什么？

用户上传一份工程图纸（PDF、DWG/DXF、IFC 或图片格式），然后可以：

- 查询图纸信息（如"E-201 上有多少个插座？"）
- 生成工程量清单
- 生成 RFI（信息请求）草稿

### 系统输出什么？

- **结构化 CIR 数据**：包含实体、连接关系、几何信息、置信度、证据链的标准化数据
- **工程量清单**：按组件类型统计的数量、面积、长度
- **自然语言回答**：带证据引用的可审计答案
- **RFI 草稿**：针对图纸中缺失或模糊信息的请求文档

### 完整流程示例

**场景**：用户上传一份电气图纸 E-101.pdf，问"E-101 上有多少个照明开关？"

| 步骤 | 做了什么                                             | 目的                                           | 涉及模块                     |
| :--- | :--------------------------------------------------- | :--------------------------------------------- | :--------------------------- |
| 1    | 用户上传 PDF 图纸                                    | 输入原始数据                                   | 前端/API                     |
| 2    | L0 Ingest：PDF → 千兆像素级分块(tiling) → CIR        | 将大图切分为模型可处理的图块，统一为标准化格式 | `ingest/`                    |
| 3    | L1 Perception：YOLO 目标检测 → 识别符号和组件        | 从图纸像素中检测出所有设备符号及其位置         | `perception/`                |
| 4    | L1 Perception：连接关系提取 → 构建连接图             | 识别哪些组件通过管线/信号相连                  | `perception/connectivity.py` |
| 5    | L2 Grounding：检测结果 → IFC 类 + MasterFormat 编码  | 将原始标签映射到行业标准分类体系               | `grounding/`                 |
| 6    | L3 Engines：生成工程量清单（counts, areas, lengths） | 统计数量，每条数据带置信度和证据链接           | `engines/takeoff.py`         |
| 7    | L4 Agent：qa.answer() 解析自然语言问题               | 将"有多少个照明开关"转为结构化查询             | `agent/qa.py`                |
| 8    | L4 Agent：查询 CIR，返回"12 个照明开关" + 证据列表   | 每个答案可追溯到具体图纸和实体ID               | `agent/qa.py`                |

## 3. 技术架构

### 技术栈概览

| 层次            | 技术                             |
| :-------------- | :------------------------------- |
| **后端 API**    | FastAPI + Pydantic v2            |
| **感知模型**    | YOLO11 (Ultralytics)             |
| **数据 schema** | Pydantic 模型，版本化 CIR        |
| **Agent 层**    | 确定性规则查询（无外部 LLM API） |
| **包管理**      | uv + Python ≥ 3.11               |

### 是否使用 LangChain/LangGraph 等技术？

**明确不使用**。项目的 Agent 层（L4）刻意避免了 LLM API 调用，采用**确定性规则匹配**的方式回答问题。这是一个非常有特色的设计决策——在工程图纸这种" liability-bearing"（承担法律责任）场景中，每个答案都必须可审计、可追溯，而 LLM 的幻觉问题在这里是不可接受的。

### 是否使用数据库或向量数据库？

**目前没有**。所有数据以 CIR（Canonical Intermediate Representation）结构化文档的形式在内存中处理。每个 CIR 文档是自包含的 JSON/序列化对象，包含图纸的所有实体、连接和元数据。

### 核心目录结构

| 模块/目录     | 作用                                                         | 关键代码                                       | 是否重点阅读 |
| :------------ | :----------------------------------------------------------- | :--------------------------------------------- | :----------- |
| `cir/`        | **CIR 核心 schema**：所有层共享的数据模型，包含 `DrawingSet`、`Entity`、`Connection` 等，带版本控制和许可证校验 | `schema.py`, `enums.py`, `serialization.py`    | ⭐⭐⭐⭐⭐        |
| `ingest/`     | **L0 数据接入**：PDF/DWG/DXF/IFC/图片 → 分块(tiling) → CIR   | `pdf.py`, `dxf.py`, `image.py`, `tiling.py`    | ⭐⭐⭐⭐         |
| `perception/` | **L1 感知层**：YOLO 目标检测 + 连接关系提取                  | `detector.py`, `adapter.py`, `connectivity.py` | ⭐⭐⭐⭐⭐        |
| `grounding/`  | **L2 语义映射**：检测标签 → IFC 类 / MasterFormat / UniFormat 编码 | `ontology.py`                                  | ⭐⭐⭐          |
| `engines/`    | **L3 算量引擎**：生成工程量清单（数量、面积、长度）          | `takeoff.py`                                   | ⭐⭐⭐⭐         |
| `agent/`      | **L4 Agent 层**：自然语言 Q&A + RFI 草稿生成（无 LLM，确定性规则） | `qa.py`, `rfi.py`                              | ⭐⭐⭐⭐⭐        |
| `backend/`    | **FastAPI 服务**：API 入口、请求路由、鉴权                   | `app.py`                                       | ⭐⭐⭐⭐         |
| `eval/`       | 评估指标、多种子置信区间、SOTA 基线对比                      | `scoreboard.py`                                | ⭐⭐⭐          |
| `synthetic/`  | 合成数据生成：IFC/参数化 → 渲染图纸                          | —                                              | ⭐⭐           |

### 请求入口与核心代码位置

| 组件           | 位置                                               |
| :------------- | :------------------------------------------------- |
| **API 入口**   | `backend/app.py` → FastAPI routes                  |
| **Agent 核心** | `agent/qa.py` → `answer()` 函数                    |
| **Prompt**     | **无 Prompt**——项目不使用 LLM，没有 prompt 工程    |
| **Tools**      | **无工具调用**——Agent 不调用外部工具，直接查询 CIR |

## 4. Agent 核心设计

### 4.1 Agent 的角色是什么？

L4 Agent 的角色是**图纸数据的"自然语言接口"**——将用户用自然语言提出的问题，转化为对结构化 CIR 的确定性查询，并返回带证据链的可审计答案。

### 4.2 Agent 如何理解用户任务？

通过**规则匹配 + 关键词解析**，而非 LLM 语义理解。`qa.answer()` 函数的核心逻辑是：

python

```
q = question.strip().lower().rstrip("?")
# 解析 "on [sheet]" 范围限定
sheet = re.search(r"\bon\s+([a-z]{1,3}-?\d[\w.-]*)", q)
# 根据关键词匹配不同查询类型
if "disciplin" in q: ...
if "sheet" in q and ("how many" in q or "count" in q): ...
# 否则按标签匹配实体
rows = _rows(ds, sheet=sheet)  # 获取所有可计数实体
matched = _match(rows, subject)  # 标签包含关键词
```



### 4.3 Agent 是否会进行任务拆解或规划？

**不会**。这是一个单步确定性查询引擎，没有任务规划或多步推理。问题被解析后直接查询 CIR 并返回结果。

### 4.4 Agent 如何决定是否调用工具？

**不调用任何工具**。所有"工具"的能力在 L0-L3 已经完成（检测、映射、算量），L4 只是**查询已经处理好的结构化数据**。

### 4.5 项目中有哪些 tools？

从传统 Agent 的"工具调用"角度看：**没有 tools**。

但从系统能力角度看，可以理解为"内置工具"：

- **检测器**（L1）：YOLO 模型识别图纸符号
- **连接提取器**（L1）：识别组件间的连接关系
- **算量引擎**（L3）：统计数量/面积/长度
- **问答引擎**（L4）：自然语言查询
- **RFI 生成器**（L4）：生成信息请求草稿

这些能力在 L0-L3 流水线中已经执行完毕，L4 不再动态调用它们。

### 4.6 是否使用 RAG、MCP 或 Skills？

| 技术       | 是否使用 | 说明                                      |
| :--------- | :------- | :---------------------------------------- |
| **RAG**    | ❌ 不使用 | 所有数据在 CIR 中结构化存储，无需向量检索 |
| **MCP**    | ❌ 不使用 | 无模型上下文协议                          |
| **Skills** | ❌ 不使用 | 无技能系统                                |

### 4.7 Agent 如何生成最终结果？

Agent 生成 `Answer` 对象，包含：

- `text`：人类可读的答案文本
- `value`：机器可读的结构化值（如 count、list）
- `evidence`：证据列表 `[(sheet_number, entity_id), ...]`

每个答案都能追溯到具体图纸和实体ID，实现**完全可审计**。

### 4.8 是否支持多轮对话、记忆或上下文管理？

**不支持**。每次问答是无状态的单次查询。项目定位是"确定性结构化查询"，而非对话系统。

### 核心调用链路

text

```
用户问题 "E-101 上有多少个照明开关？"
    ↓
backend/app.py: POST /qa
    ↓
agent/qa.py: answer(ds, question)
    ↓
解析 "on E-101" → sheet = "E-101"
解析 "照明开关" → subject = "照明开关"
    ↓
_rows(ds, sheet="E-101") → 获取该图纸所有实体
_match(rows, "照明开关") → 过滤标签包含"照明开关"的实体
    ↓
返回 Answer(
    text="12 个照明开关",
    value=12,
    evidence=[("E-101", "ent_001"), ("E-101", "ent_002"), ...]
)
    ↓
FastAPI 返回 JSON 响应
```

| **企业级补充**     | —                                                            | 缺少：任务队列、异步处理、分布式部署、Webhook、数据持久化 | 增加 Celery/RQ 处理大图纸；增加 PostgreSQL 存储 CIR 历史；增加图纸版本管理 |

### 额外可落地性分析

**适合场景**：

- 企业内部图纸数据库的智能化查询
- 工程造价软件的 AI 插件
- BIM 工作流中的数据抽取工具

**不适合场景**：

- 需要多轮对话的交互式助手
- 需要实时流式处理的场景
- 图纸种类极其多样、缺乏训练数据的场景

## 6. 总结与学习价值

### 6.1 核心亮点

1. **CIR（规范化中间表示）是最大的亮点**：所有层共享一个 schema，实现了"一次结构化，多次使用"。这是数据驱动型 Agent 的最佳实践。
2. **"无 LLM 的 Agent"设计哲学**：在 liability-bearing 场景中，用确定性规则代替 LLM 幻觉，每个答案都可审计。这打破了"Agent 必须用 LLM"的刻板印象。
3. **证据链设计**：每个实体、每条算量数据都携带 `confidence`、`source_bbox`、`produced_by`、`model_version`，实现了从"模型输出"到"人工可验证"的闭环。
4. **许可证合规内置**：CIR 在 schema 层面强制区分 `research` 和 `commercial` 数据流，防止商业使用中混入非商业许可的数据。
5. **模块化五层架构**：Ingest → Perception → Grounding → Engines → Agent，每层职责清晰，可独立替换或优化。

### 6.2 不足

1. **Agent 能力有限**：只支持预定义的几种查询模式（count、list、presence、disciplines、sheets），无法处理复杂推理问题（如"哪些回路负载超过了设计容量？"）
2. **无 LLM 的代价**：无法理解同义词、模糊表达或复杂语义。用户必须用特定关键词提问。
3. **无持久化存储**：每次请求都要重新处理图纸，无法复用已处理的 CIR。
4. **缺乏多模态输出**：无法在答案中返回图纸截图或高亮标记。

### 6.3 哪些设计值得学习？

1. **CIR 模式**：任何数据密集型 Agent 都应该定义自己的"规范化中间表示"，让数据处理和用户交互解耦。
2. **证据追溯**：每个输出都带证据链——这是企业级 AI 应用的必备能力。
3. **模块化分层**：感知 → 理解 → 推理 → 交互的分层架构，可推广到其他领域的 Agent 设计。
4. **"先结构化，再问答"**：与其让 LLM 直接看图回答，不如先用专用模型提取结构化数据，再用确定性逻辑查询——更准确、更可控、更可审计。

### 6.4 哪些设计不适合直接照搬？

1. **完全不用 LLM**：在通用场景中，LLM 的语义理解能力不可或缺。更好的做法是"LLM 做意图理解 + 规则引擎做数据查询"的混合架构。
2. **无状态设计**：生产环境需要对话记忆和上下文管理。
3. **硬编码查询规则**：当查询类型增多时，维护成本急剧上升。应考虑用声明式配置或 DSL。

### 6.5 二次开发优先级

1. **第一优先**：增加 LLM 意图理解层——将用户自然语言转为结构化查询参数，保持数据查询层的确定性
2. **第二优先**：增加 CIR 持久化存储（PostgreSQL JSONB 或 MongoDB），避免重复处理
3. **第三优先**：扩展查询能力——支持更复杂的聚合、筛选和连接查询
4. **第四优先**：增加多轮对话和上下文管理

### 6.6 面试表达

> **项目背景**：ConstructDrawingAI 是一个面向建筑、工程和施工行业的图纸理解系统，目标是将二维工程图纸（电气图、建筑图、P&ID 流程图）转化为结构化、可决策的数据。核心痛点是传统造价和工程团队需要人工翻阅图纸来统计设备数量、追踪连接关系，耗时且易错。
>
> **技术架构**：项目采用五层架构——L0 Ingest 负责多格式图纸接入和分块，L1 Perception 用 YOLO11 做符号检测和连接提取，L2 Grounding 将检测结果映射到 IFC 类和 MasterFormat 编码，L3 Engines 生成工程量清单，L4 Agent 提供自然语言 Q&A。所有层共享一个统一的 Canonical Intermediate Representation（CIR）schema，基于 Pydantic v2 实现版本化和许可证校验。后端用 FastAPI 提供服务。
>
> **Agent 工作流**：用户上传图纸后，经过 L0-L3 的流水线处理生成 CIR 结构化数据。用户提问时，Agent 层通过规则匹配解析问题中的关键词和图纸范围，然后直接查询 CIR 返回结果。每个答案都携带 evidence 字段，精确追溯到具体图纸和实体 ID，实现完全可审计。
>
> **Tools / RAG / MCP 使用情况**：这个项目的特殊之处在于，它的 Agent 层**刻意不使用 LLM**，也没有 RAG、MCP 或传统意义上的工具调用。原因是在工程图纸这种承担法律责任的场景中，幻觉是不可接受的，所以采用确定性规则查询代替 LLM 生成。视觉理解能力在 L1 层通过 YOLO 模型实现，算量能力在 L3 层通过规则引擎实现，L4 只做查询。
>
> **项目亮点**：一是 CIR 设计——所有层共享同一 schema，实现了"一次结构化，多次使用"；二是证据链设计——每个输出都带置信度和来源追溯，满足企业级审计要求；三是内置许可证合规校验，区分研究用途和商业用途的数据流。
>
> **企业级落地思考**：如果要投入生产，我会优先增加 LLM 意图理解层来提升自然语言交互的鲁棒性，同时保持数据查询层的确定性；其次增加 CIR 的持久化存储避免重复计算；另外需要补充任务队列处理大图纸、RBAC 权限控制和结构化日志监控。这个项目的 CIR 模式和证据链设计非常值得借鉴，但无状态的硬编码查询规则需要改造才能支撑复杂的企业场景。
