## 1. 项目定位

### 1.1 这个项目是做什么的？

`agency-agents-zh` 是一个**AI 专家角色定义库**，本质上是英文原版 `agency-agents` 的中文社区版。项目提供了 **268 个即插即用的 AI 专家角色定义**，覆盖工程、设计、营销、产品、游戏、安全、GIS、金融等 20 个部门。每个角色都以**标准化 Markdown 文件**存储，包含独立的人设、专业流程和可交付成果。

在完整翻译上游 215 个英文角色的基础上，项目新增了 **53 个中国市场原创智能体**，涵盖小红书、抖音、微信、B站、飞书、钉钉等平台运营，以及跨境电商、政务 ToG、医疗合规、Qt 工业上位机、机械设计、畜禽养殖档案核对等垂直领域。

### 1.2 它解决了什么业务问题？

该项目主要解决三个核心痛点：

1. **通用大模型角色漂移**：通用 LLM 缺乏稳定的角色定位，同一问题在不同对话中可能给出风格迥异的回答。该项目通过预定义的专家角色提示词，固化角色设定，确保输出风格和专业度一致。
2. **多角色协作上下文断裂**：当需要多个专家协同工作时，上下文管理和角色切换容易出错。项目通过标准化的角色定义格式，为多智能体协作提供了统一的"角色资产"基础。
3. **产出无交付标准**：通用对话缺乏结构化的输出格式。每个角色定义中都包含**可交付成果**的描述，引导 LLM 按专业标准输出。

### 1.3 目标用户是谁？

- **AI 工具使用者**：使用 Claude Code、Cursor、Copilot、Hermes Agent、OpenClaw 等 18 种 AI 编程工具的开发者和创作者
- **企业团队**：希望快速组建"虚拟专家团队"的产品、运营、营销团队
- **AI 应用开发者**：基于角色库二次开发多智能体系统的工程师
- **个人创作者**：需要专业领域 AI 助手的独立开发者、自由职业者

### 1.4 它属于哪一类 Agent？

**工作流 Agent / 多 Agent 系统**（角色资产层）

准确来说，`agency-agents-zh` 本身是 **Agent 的"角色定义资产库"**，而非完整的 Agent 运行时。它提供的是 **Agent 的"大脑"（人设 + 专业流程）**，而非"身体"（执行引擎）。搭配官方编排器 `agency-orchestrator` 后，可构成完整的多 Agent 工作流系统——一句话即可让多位专家按 DAG 自动协作。

### 1.5 为什么这个项目需要用 Agent，而不是普通应用？

普通应用（如传统的客服系统或规则引擎）只能处理预定义的固定流程，无法应对开放域的专业咨询和创作任务。而该项目中的每个角色都是一个 **"专业领域专家"**：

- 它需要理解用户的**自然语言任务描述**
- 它需要基于**专业领域知识**提供结构化的可交付成果
- 它需要支持**多轮对话**和**上下文理解**
- 它可以被**动态组合**成多专家协作团队

这些能力天然需要 LLM + Agent 架构来实现，普通应用无法胜任。

## 2. 业务流程

### 2.1 用户输入什么？

用户输入**自然语言的任务描述或问题**，例如："帮我写一份小红书种草文案"、"设计一个电商大促的营销方案"、"审查这段代码的安全漏洞"。

### 2.2 系统输出什么？

系统输出**结构化的专业成果**，包括但不限于：文案、设计方案、代码审查报告、营销策略文档、产品需求文档、数据分析报告等，具体格式取决于所选角色的专业领域。

### 2.3 从用户输入到最终结果，中间经历了哪些步骤？

以用户使用 **`agency-orchestrator`** 编排器为例，完整流程如下：

| 步骤          | 做了什么                                           | 目的                                      | 涉及模块                       |
| :------------ | :------------------------------------------------- | :---------------------------------------- | :----------------------------- |
| 1. 角色选择   | 用户从 268 个角色中选择一个或多个专家              | 确定任务所需的专业领域和专家组合          | 角色库（各领域 `.md` 文件）    |
| 2. 任务输入   | 用户用自然语言描述任务需求                         | 将业务需求转化为 Agent 可理解的指令       | 用户界面 / CLI                 |
| 3. 任务解析   | 编排器解析用户意图，识别任务类型和所需专家         | 将自然语言映射到具体的 Agent 角色和工作流 | `agency-orchestrator` 编排引擎 |
| 4. 工作流编排 | 按 DAG（有向无环图）组织多个专家的执行顺序         | 确保多专家协作的依赖关系和执行顺序正确    | 编排器 DAG 引擎                |
| 5. 角色加载   | 从 `agency-agents-zh` 加载对应角色的 Markdown 定义 | 将人设、专业流程和输出标准注入 LLM 上下文 | 角色库加载模块                 |
| 6. LLM 推理   | 各专家角色依次或并行调用 LLM 执行子任务            | 每个专家在自己的专业领域内生成高质量输出  | LLM API（支持 11 种提供商）    |
| 7. 结果汇总   | 编排器收集所有专家的输出，按预设格式汇总           | 形成完整的、结构化的最终交付物            | 编排器汇总模块                 |
| 8. 验收核验   | 自动验证输出是否符合预设标准                       | 确保交付质量，减少人工复核成本            | 自动验收模块                   |

### 2.4 具体例子

**用户输入**："我要做一个抖音美妆账号，帮我出一套完整的起号方案"

**完整流程**：

1. **角色选择**：系统自动匹配「抖音运营专家」「内容策略师」「短视频剪辑指导师」三个角色
2. **任务输入**：用户描述"美妆账号起号方案"
3. **任务解析**：编排器识别出需要账号定位、内容规划、运营策略三个子任务
4. **DAG 编排**：内容策略师 → 抖音运营专家 → 短视频剪辑指导师（依赖关系）
5. **角色加载**：从 `marketing/` 目录加载三个角色的 Markdown 定义
6. **LLM 推理**：内容策略师输出账号定位和内容方向 → 抖音运营专家输出运营节奏和投流策略 → 剪辑指导师输出视频风格和剪辑规范
7. **结果汇总**：生成一份包含定位、内容、运营、剪辑的完整起号方案文档
8. **验收核验**：自动检查方案是否覆盖所有必要模块

## 3. 技术架构

### 3.1 前端、后端、Agent 服务分别用什么技术？

`agency-agents-zh` 本身**不包含前端、后端或 Agent 服务代码**——它是一个纯角色定义库。但配套的 `agency-orchestrator` 提供了完整的技术栈：

| 层级            | 技术                                             |
| :-------------- | :----------------------------------------------- |
| 前端 / 桌面端   | Web Studio / 原生桌面 App（macOS/Windows/Linux） |
| 后端 / 编排引擎 | Node.js / npm 包                                 |
| Agent 服务      | 支持 11 种 LLM 提供商，其中 7 种免 API Key       |
| 部署方式        | 网页 / 桌面 / Docker 全渠道                      |

### 3.2 是否使用 LangChain、LangGraph、Deep Agents 等技术？

根据公开信息，该项目**未明确使用 LangChain 或 LangGraph**。其技术路线更偏向**轻量化**：

- **角色定义**：纯 Markdown 驱动，无复杂框架依赖
- **编排引擎**：自研 DAG 工作流引擎，非 LangGraph
- **集成方式**：角色定义可被 18 种 AI 工具直接加载

### 3.3 是否使用数据库或向量数据库？

`agency-agents-zh` 作为角色库，**不使用任何数据库**——所有角色以 Markdown 文件存储，通过文件系统读取。`agency-orchestrator` 的公开信息中**未提及向量数据库**的使用，推测其采用纯 LLM 推理 + 提示词工程的方式，未引入 RAG 向量检索。

### 3.4 项目的核心目录分别负责什么？

| 目录           | 作用                                        | 是否重点阅读 |
| :------------- | :------------------------------------------ | :----------- |
| `engineering/` | 工程类专家角色（架构师、DevOps、前后端等）  | ✅            |
| `design/`      | 设计类专家角色（UI/UX、平面设计等）         | ✅            |
| `marketing/`   | 营销类专家角色（SEO、私域、小红书、抖音等） | ✅            |
| `product/`     | 产品类专家角色（PM、需求分析等）            | ✅            |
| `finance/`     | 金融类专家角色                              | ✅            |
| `security/`    | 安全类专家角色                              | ✅            |
| `gaming/`      | 游戏类专家角色                              | ✅            |
| `gis/`         | GIS 地理信息专家角色                        | ✅            |
| `.github/`     | GitHub 配置（Issue 模板、赞助配置等）       | ❌            |

### 3.5 请求入口、Agent 核心代码、Prompt、Tools、RAG 逻辑分别在哪里？

| 组件                   | 位置                              | 说明                                           |
| :--------------------- | :-------------------------------- | :--------------------------------------------- |
| **请求入口**           | `agency-orchestrator`（独立项目） | 不在本仓库内                                   |
| **Agent 核心代码**     | `agency-orchestrator`（独立项目） | 编排引擎和 LLM 调用逻辑                        |
| **Prompt（角色定义）** | 各领域目录下的 `.md` 文件         | 每个角色文件包含人设、专业流程、输出标准       |
| **Tools**              | 未在公开信息中提及                | 推测由各集成工具（Claude Code、Cursor 等）提供 |

## 4. Agent 核心设计

> 以下分析基于 `agency-agents-zh` 作为**角色定义库**的定位，其 Agent 行为由集成该角色库的 AI 工具（如 Claude Code、Cursor）或编排器（`agency-orchestrator`）实际执行。

### 4.1 Agent 的角色是什么？

每个 Agent 角色都是一个**垂直领域的专家**，拥有：

- **独立人设**：性格、语气、沟通风格
- **专业领域**：擅长的具体业务场景
- **专业流程**：完成任务的标准化工作流
- **可交付成果**：输出的格式和标准

### 4.2 Agent 如何理解用户任务？

Agent 通过**角色定义文件中的专业流程和领域知识**来理解用户任务。当用户提出需求时，Agent 会基于其预设的角色定位，将用户问题映射到专业领域的任务框架中。

### 4.3 Agent 是否会进行任务拆解或规划？

在多 Agent 协作场景下（使用 `agency-orchestrator`），**会进行任务拆解和 DAG 规划**。编排器将用户的自然语言任务拆解为多个子任务，按依赖关系分配给不同的专家角色，形成 DAG 工作流。

### 4.4 Agent 如何决定是否调用工具？

工具调用能力**取决于集成该角色库的具体 AI 工具**（如 Claude Code、Cursor 的 Tool Use 功能），而非角色定义本身。角色定义文件**不包含工具调用的逻辑**。

### 4.5 项目中有哪些 Tools？

`agency-agents-zh` 本身**不定义 Tools**。但项目支持集成到 18 种 AI 编程工具中，这些工具各自提供不同的 Tool 能力（如文件读写、代码执行、浏览器操作等）。

### 4.6 是否使用 RAG、MCP 或 Skills？

| 技术       | 是否使用   | 说明                                                |
| :--------- | :--------- | :-------------------------------------------------- |
| **RAG**    | ❌ 未使用   | 角色定义基于固定提示词，无向量检索                  |
| **MCP**    | ❌ 未使用   | 公开信息中未提及 MCP（Model Context Protocol）      |
| **Skills** | ⚠️ 部分支持 | 每个角色定义可视为一个"Skill"，但非标准化的技能系统 |

### 4.7 Agent 如何生成最终结果？

Agent 通过 LLM 推理生成结果，核心流程是：

1. 将角色定义文件（Markdown）作为**系统提示词**注入 LLM
2. 将用户任务作为**用户消息**传入
3. LLM 基于角色设定和专业流程生成结构化输出
4. 在多 Agent 场景下，各专家的输出被编排器汇总为最终交付物

### 4.8 是否支持多轮对话、记忆或上下文管理？

支持程度**取决于集成该角色库的具体工具**：

- **单角色对话**：在 Claude Code、Cursor 等工具中，支持多轮对话和上下文管理
- **多角色协作**：`agency-orchestrator` 支持多专家协作的上下文传递
- **长期记忆**：公开信息中未提及持久化的记忆机制

## 5. 工程化与可落地性

| 维度                | 当前实现                                     | 不足                                              | 改进建议                                                     |
| :------------------ | :------------------------------------------- | :------------------------------------------------ | :----------------------------------------------------------- |
| **异常处理**        | 由集成工具（Claude Code、Cursor 等）各自处理 | 角色定义本身无异常处理逻辑                        | 在编排器中增加 LLM 调用重试、超时、降级机制                  |
| **日志和监控**      | 未在项目中体现                               | 无统一日志和监控体系                              | 集成 OpenTelemetry 等可观测性工具，记录每次 Agent 调用的 token 消耗、延迟和输出质量 |
| **权限控制**        | 无                                           | 任何人都可加载任何角色，无访问控制                | 增加角色级别的 RBAC（基于角色的访问控制），区分查看、使用、编辑权限 |
| **工具调用安全**    | 由集成工具负责                               | 角色定义无法约束工具调用范围                      | 在角色定义中增加 `allowed_tools` 字段，限制每个角色可调用的工具白名单 |
| **RAG 未命中处理**  | N/A（未使用 RAG）                            | 无知识库检索能力，只能依赖 LLM 内部知识           | 如需引入 RAG，需增加向量数据库和知识库管理模块               |
| **扩展新工具/场景** | ✅ 支持——新增角色只需添加 Markdown 文件       | 新增角色需手动编写，无自动化生成工具              | 开发角色生成器，基于模板快速创建新角色；建立角色审核流程     |
| **企业级落地**      | 可作为角色资产库使用                         | 缺少企业级功能：SSO、审计日志、用量统计、SLA 保障 | 补充企业级功能模块，或基于 `agency-orchestrator` 进行二次开发 |

## 6. 总结与学习价值

### 6.1 核心亮点

1. **角色资产化**：将 Agent 角色定义为可复用的 Markdown 资产，而非硬编码在代码中，极大提升了可维护性和可扩展性
2. **中文优先**：项目专门针对中文场景优化，新增了 53 个中国市场原创角色，覆盖抖音、小红书、微信等本土平台
3. **即插即用**：支持 18 种主流 AI 工具，角色定义可被多种工具直接加载
4. **生态完整**：配套 `agency-orchestrator` 提供从单角色到多角色 DAG 协作的完整能力
5. **零代码 / 低门槛**：非技术人员也可以通过 Markdown 理解和修改角色定义

### 6.2 不足

1. **非独立 Agent 框架**：项目本身是角色库，不能独立运行，需要依赖其他工具或编排器
2. **无 RAG 支持**：无法接入企业私有知识库，限制了在垂直领域的深度应用
3. **无原生 Tool Calling**：工具调用能力完全依赖集成工具，角色定义无法精细控制工具使用
4. **缺少工程化能力**：无日志、监控、权限控制、审计等企业级功能
5. **角色质量参差不齐**：268 个角色由社区贡献，质量和深度不一

### 6.3 值得学习的设计

1. **Markdown 驱动的 Agent 定义**：用纯文本格式定义 Agent 角色，降低门槛、提升可维护性
2. **角色即资产**的理念：将 Agent 的"大脑"与"执行引擎"解耦，实现角色复用和跨平台移植
3. **中文场景的本土化深耕**：不是简单翻译，而是针对中国市场的实际业务场景新增角色
4. **DAG 多智能体协作**：通过有向无环图组织多个专家有序协作

### 6.4 不适合直接照搬的设计

1. **纯文件系统的角色存储**：大规模企业场景下，文件系统难以支撑版本管理、权限控制和热更新，应考虑迁移到配置中心或数据库
2. **无结构化输出的角色定义**：每个角色的输出格式是自然语言描述，而非 JSON Schema，不利于程序化解析和验收
3. **角色与工具的松耦合**：角色定义无法声明自己需要哪些工具，导致在工具选择上缺乏确定性

### 6.5 二次开发优先改造建议

1. **增加角色 Schema 校验**：为每个角色定义增加 JSON Schema，确保输出格式可程序化解析
2. **引入向量数据库**：将角色定义向量化，支持语义检索和动态角色匹配
3. **增加工具绑定**：在角色定义中增加 `tools` 字段，声明该角色可调用的工具白名单
4. **构建角色管理后台**：提供角色的 CRUD、版本管理、审核流程和权限控制
5. **接入企业 SSO 和审计日志**：满足企业级安全合规要求

### 6.6 面试表达

> **项目背景**：`agency-agents-zh` 是一个开源的中文 AI 专家角色库，包含 268 个覆盖 20 个业务部门的即插即用 Agent 角色定义。它是英文原版 `agency-agents` 的中文社区版，由 jnMetaCode 维护，在完整翻译 215 个英文角色的基础上，新增了 53 个中国市场原创角色。
>
> **技术架构**：项目的核心设计理念是 **"角色即资产"**——所有 Agent 角色以标准化 Markdown 文件存储，每个角色文件包含独立的人设、专业流程和可交付成果。它本身是一个角色定义库，不包含前端、后端或运行时引擎，但可以无缝集成到 Claude Code、Cursor、Copilot 等 18 种 AI 编程工具中。配套的编排器 `agency-orchestrator` 提供了完整的 DAG 多智能体协作能力，支持 11 种 LLM 提供商，可通过网页、桌面客户端或 Docker 部署。
>
> **Agent 工作流**：在典型的业务流程中，用户通过自然语言描述任务需求，编排器将任务拆解为多个子任务并按 DAG 分配给对应的专家角色。每个角色加载对应的 Markdown 定义作为系统提示词，调用 LLM 在各自专业领域生成输出，最后由编排器汇总为完整的可交付成果。
>
> **Tools / RAG / MCP / Skills 使用情况**：项目本身不定义 Tools 和 RAG 逻辑，工具调用能力完全依赖集成工具（如 Claude Code 的 Tool Use）提供。未使用 MCP（Model Context Protocol）。每个角色定义可视为一个领域特定的"Skill"，但非标准化的技能系统。
>
> **项目亮点**：一是 **中文优先**的设计理念，针对抖音、小红书、微信等本土平台新增了 50+ 个原创角色；二是 **角色与执行引擎解耦**的架构，使角色定义可以在多种工具间复用；三是 **零代码门槛**，非技术人员也可以通过 Markdown 理解和修改角色。
>
> **企业级落地思考**：该项目作为角色资产库非常有价值，但直接用于企业生产环境还需要补充几个关键能力：引入向量数据库支持 RAG 知识检索、增加 JSON Schema 确保输出可程序化解析、建立角色版本管理和权限控制体系、接入 SSO 和审计日志满足合规要求。如果基于它二次开发，建议优先改造角色 Schema 和增加工具绑定能力，让每个角色可以声明自己需要调用的工具白名单。
