## 1. 项目定位

### 1.1 项目是做什么的？

ShopAssist Agent 是一个面向电商购物与售后场景的智能客服 Agent 系统。项目将大模型、工具调用、RAG 检索、图谱查询和多轮会话管理结合起来，构建一个贴近真实购物售后流程的客服 Agent。

### 1.2 解决了什么业务问题？

项目来源于日常购物中的真实痛点：传统 AI 客服经常答非所问、上下文记不住、退货退款判断慢、复杂售后问题容易反复转人工。ShopAssist Agent 通过以下能力解决这些问题：

- **多轮上下文理解**：用户连续追问时可以结合历史对话理解意图
- **多源数据查询**：支持订单、商品、售后政策、用户信息等多类数据查询
- **视觉理解能力**：支持图片入口，用于商品破损、错发、外包装异常等售后判断
- **知识增强问答**：支持文件 RAG、GraphRAG 和 Neo4j 图谱查询

### 1.3 目标用户是谁？

- 电商平台运营方（需要替代或增强人工客服）
- 有售后咨询需求的普通消费者
- 对 AI 客服感兴趣的技术开发者和架构师

### 1.4 属于哪一类 Agent？

**客服 Agent**。系统专门面向电商购物与售后场景，支持订单查询、退款退货判断、商品咨询、图片理解、知识库问答和人工介入判断。

### 1.5 为什么需要用 Agent，而不是普通应用？

普通客服机器人本质是"规则匹配 + 模板回复"，无法应对复杂售后场景。ShopAssist Agent 之所以称为 Agent，在于其具备**自主决策能力**：

| 维度     | 普通应用     | Agent 方案                      |
| :------- | :----------- | :------------------------------ |
| 意图理解 | 关键词匹配   | LLM 语义理解 + 动态路由         |
| 任务处理 | 固定流程     | LangGraph 编排 + 动态工具调用   |
| 知识调用 | 静态 FAQ     | RAG + GraphRAG + Neo4j 多路检索 |
| 上下文   | 单轮或无状态 | 多轮会话 + 记忆管理             |

## 2. 业务流程

### 2.1 用户输入什么？

用户可以通过文本输入问题（如"订单现在是什么状态？""收到的商品坏了怎么办？"），也可以上传图片或文件。

### 2.2 系统输出什么？

系统输出流式客服回复，包含解决方案、操作建议或转人工提示。

### 2.3 完整流程

| 步骤             | 做了什么                                                     | 目的                           | 涉及模块                    |
| :--------------- | :----------------------------------------------------------- | :----------------------------- | :-------------------------- |
| 1. 用户输入      | 用户输入文本/图片/文件                                       | 发起咨询请求                   | 前端 / API 路由             |
| 2. 意图识别      | LLM 将问题分类为 general / additional / graphrag / image / file | 确定后续处理路径               | `lg_prompts.py` + LangGraph |
| 3. 安全护栏      | 检查用户问题是否与图谱/业务相关                              | 防止无关问题进入检索链路       | `guardrails` 节点           |
| 4. 任务规划      | Planner 节点拆分子任务                                       | 将复杂问题分解为可执行的子任务 | `planner.node`              |
| 5. 工具/RAG 调用 | 根据意图调用对应工具或检索                                   | 获取回答所需的业务数据或知识   | `multi_tool` 工作流         |
| 6. Neo4j 查询    | 对结构化关系数据进行图谱查询                                 | 查询订单、商品、用户等关系数据 | `kg_sub_graph`              |
| 7. 幻觉检测      | 检查生成的回复是否有事实幻觉                                 | 保证回复准确性                 | `CHECK_HALLUCINATIONS`      |
| 8. 最终回复生成  | LLM 综合所有信息生成客服回复                                 | 输出给用户                     | 最终回复节点                |

### 2.4 具体例子

用户问："我上周买的手机坏了，能退吗？"

1. **意图识别**：LLM 判断为 `graphrag-query`（需要查询售后政策 + 订单信息）
2. **安全护栏**：确认问题与电商售后相关，继续处理
3. **Planner**：拆分为"查询订单状态"和"查询退货政策"两个子任务
4. **工具调用**：通过 Neo4j 查询用户订单信息 + RAG 检索退货政策
5. **幻觉检测**：检查回复是否基于事实
6. **生成回复**：输出"亲～您的订单#12345 在退货期内，根据政策可以申请退货退款，请点击..."

## 4. Agent 核心设计

### 4.1 Agent 的角色是什么？

电商智能客服。角色定位是"帮助用户解决与产品、订单、售后和技术支持相关的问题"，采用类似淘宝/京东客服的亲切、专业语气。

### 4.2 Agent 如何理解用户任务？

通过 Prompt-template + 大模型完成意图识别，将用户问题划分为 5 类：

- `general-query`：普通问答，不需要查询知识库
- `additional-query`：需要补充信息
- `graphrag-query`：需要知识库或图谱检索
- `image-query`：图片相关问题
- `file-query`：文件问答问题

### 4.3 Agent 是否会进行任务拆解或规划？

**会**。LangGraph 编排流程中包含 **Planner 节点**，负责子任务拆分。在 `multi_tool` 工作流中，Planner 将复杂问题分解为多个可执行的子任务，再分配给不同的工具。

### 4.4 Agent 如何决定是否调用工具？

通过 **Function Calling** 机制。模型在收到用户问题后，自动判断是否需要调用工具，并选择具体的工具和参数。工具调用采用 `tool_choice="auto"` 模式，让模型自主决策。

### 4.5 项目中有哪些 tools？

从代码中可以看到：

| 工具              | 说明                               |
| :---------------- | :--------------------------------- |
| `SearchTool`      | 搜索工具，用于检索外部信息         |
| 图谱查询工具      | 通过 Neo4j 查询结构化关系数据      |
| Cypher 查询工具   | 执行预定义或动态生成的 Cypher 查询 |
| GraphRAG 查询工具 | 自定义图谱 RAG 查询                |

工具通过 `ToolRegistry` 统一注册和管理。

### 4.6 是否使用 RAG、MCP 或 Skills？

| 技术               | 使用情况                                                   |
| :----------------- | :--------------------------------------------------------- |
| **RAG**            | ✅ 文件 RAG：售后政策、商品说明、FAQ 等非结构化内容进入 RAG |
| **GraphRAG**       | ✅ 文档、实体、关系和社区摘要结合的知识增强问答             |
| **Neo4j 图谱查询** | ✅ 订单、商品、用户、售后记录等结构化关系查询               |
| **MCP**            | ❌ 未使用                                                   |
| **Skills**         | ❌ 未使用（通过 Tools 替代）                                |

### 4.7 Agent 如何生成最终结果？

流程：**用户问题 → 意图识别 → 安全护栏 → Planner 拆解 → 工具/RAG 调用 → 幻觉检测 → LLM 生成 → 返回结果**。

关键步骤：

1. **路由判断**：`analyze_and_route_query` 函数通过 LLM 分类用户问题
2. **工具执行**：`multi_tool` 工作流选择并执行工具
3. **幻觉检测**：`CHECK_HALLUCINATIONS` 检查生成内容是否基于事实
4. **最终回复**：综合所有信息生成客服风格的回复

### 4.8 是否支持多轮对话、记忆或上下文管理？

**支持**。

- **多轮对话**：通过 `Conversation` 和 `Message` 模型持久化存储对话历史
- **上下文管理**：LangGraph 的 `AgentState` 使用 `add_messages` 累加消息历史
- **记忆**：使用 `MemorySaver` 作为 checkpointer
- **会话管理**：`ConversationService` 负责会话的创建、更新和查询

## 6. 总结与学习价值

### 6.1 核心亮点

1. **完整的技术栈组合**：LangGraph + RAG + GraphRAG + Neo4j + Redis 语义缓存，展示了 Agent 系统的完整拼图
2. **LangGraph 精细化编排**：将客服链路拆分为 8 个独立节点（意图识别→护栏→Planner→工具调用→RAG→图谱查询→幻觉检测→回复生成），流程可控、问题可定位
3. **多路知识增强**：同时支持文件 RAG、GraphRAG 和 Neo4j 图谱查询，兼顾非结构化文档和结构化关系数据
4. **语义缓存**：Redis + 本地 embedding 对高频相似问题进行缓存，降低 API 成本和响应延迟
5. **Agent Harness 层**：统一管理模型选择、工具注册、路由策略和执行日志

### 6.2 不足

1. **缺少测试**：未发现单元测试和集成测试代码，企业级落地风险较高
2. **缺少容器化**：没有 Docker Compose 或 K8s 部署配置
3. **RAG 降级策略不明确**：检索未命中时如何处理没有明确说明
4. **工具安全机制较弱**：缺少工具调用的审计日志和速率限制
5. **MCP 未使用**：没有采用 Model Context Protocol 标准

### 6.3 哪些设计值得学习？

1. **LangGraph 状态机设计**：用 StateGraph 定义清晰的工作流节点和边，比直接写 ReAct Loop 更可控
2. **AgentState 设计**：通过 `add_messages` 实现消息的增量累加，优雅地管理多轮对话上下文
3. **意图识别与路由分离**：先分类再路由，而不是让模型直接决策，降低出错概率
4. **幻觉检测节点**：在生成回复后增加幻觉检测，保证回答的可靠性
5. **多工具工作流抽象**：`create_multi_tool_workflow` 将 Planner → Tool Selection → Execution 封装为可复用的工作流

### 6.4 哪些设计不适合直接照搬？

1. **硬编码的 Prompt**：提示词直接写在代码中，不适合频繁迭代
2. **单一 LLM 供应商依赖**：虽然支持 DeepSeek 和 Ollama，但切换成本较高
3. **过于复杂的图结构**：`kg_sub_graph` 层级较深，理解和维护成本高
4. **CORS 全开**：`allow_origins=["*"]`不适合生产环境

### 6.5 二次开发优先改动建议

1. **提取 Prompt 到外部配置**：将 `lg_prompts.py` 中的提示词移到 YAML/JSON 配置或数据库
2. **补充测试用例**：为核心节点（意图识别、工具调用、RAG 检索）编写单元测试
3. **增加 Docker 部署**：编写 Dockerfile 和 docker-compose.yml
4. **完善 RAG 降级**：增加检索置信度阈值 + 未命中时的友好回复
5. **接入可观测性**：增加 OpenTelemetry 或 Prometheus 指标
6. **工具安全加固**：增加工具调用的审计日志和速率限制

### 6.6 面试表达

> **项目背景**：ShopAssist Agent 是一个面向电商购物与售后场景的智能客服 Agent 系统。项目源于传统 AI 客服答非所问、上下文记不住、复杂售后问题容易反复转人工的真实痛点。系统支持订单查询、退款退货判断、商品咨询、图片理解、知识库问答和人工介入判断。
>
> **技术架构**：后端使用 Python + FastAPI，前端使用 Vue。Agent 编排层基于 LangGraph 和 LangChain，将客服链路拆分为意图识别、安全护栏、Planner 拆解、工具调用、RAG/GraphRAG 检索、Neo4j 图谱查询、幻觉检测和最终回复生成 8 个独立节点。数据层使用 MySQL 存储业务数据、Neo4j 存储结构化关系数据、Redis 做语义缓存。
>
> **Agent 工作流**：用户输入问题后，系统首先通过 LLM 进行意图识别（general/additional/graphrag/image/file 五分类），然后经过安全护栏过滤，Planner 节点将复杂问题拆解为子任务，通过 Function Calling 机制让模型自动选择并调用工具，结合 RAG/GraphRAG 检索和 Neo4j 图谱查询获取知识，最后经过幻觉检测生成客服风格的回复。
>
> **Tools / RAG / 知识增强**：项目支持文件 RAG（处理售后政策、商品说明等非结构化文档）、GraphRAG（结合文档、实体、关系和社区摘要）和 Neo4j 图谱查询（处理订单、商品、用户等结构化关系数据）。工具通过 ToolRegistry 统一注册，模型通过 Function Calling 自主决策调用。
>
> **项目亮点**：一是 LangGraph 精细化编排，流程可控、问题可定位；二是多路知识增强（RAG + GraphRAG + Neo4j）兼顾非结构化和结构化数据；三是 Redis 语义缓存降低高频问题的 API 成本；四是 Agent Harness 层统一管理模型、工具和日志。
>
> **企业级落地思考**：当前项目在技术选型和架构设计上有很好的参考价值，但要落地企业级生产环境，还需要补充：完善的单元测试和集成测试、Docker 容器化部署、RAG 未命中时的降级策略、工具调用的审计日志和速率限制、以及 Prometheus/Grafana 可观测性体系。
