## 1. 项目定位

### 1.1 这个项目是做什么的？

**CAD-BOQ Pipeline** 是一个将 CAD 工程图纸自动转化为工程量清单（BOQ，Bill of Quantities）的全流程自动化工作流项目。它接收 DXF/DWG 格式的 CAD 图纸，经过识图、审图、算量、编清单、组价五个步骤，最终输出包含价格信息的 Excel 工程量清单。

### 1.2 它解决了什么业务问题？

在建筑工程领域，从 CAD 图纸到工程量清单的转化传统上依赖造价工程师人工完成——肉眼识图、手动计算工程量、查阅定额手册套价。这个过程耗时数天至数周，且容易出错。该项目试图用自动化流水线替代人工重复劳动，将“图纸 → 清单”的转化从“人读图、人算量、人套价”变为“机器读图、规则算量、数据套价”。

### 1.3 目标用户是谁？

- **造价咨询公司**：需要快速出工程量清单和报价
- **施工单位**：投标报价阶段的工程量测算
- **设计院**：设计概算编制
- **工程审计机构**：工程量复核

### 1.4 它属于哪一类 Agent？

**工作流 Agent（Workflow Agent）** 。

严格来说，这是一个 **Pipeline 型 Agent** ——它按照固定五步顺序执行（识图→审图→算量→编清单→组价），每一步是确定性规则引擎，中间穿插 LLM 视觉识别能力。它不像 ReAct 型 Agent 那样自主决策调用什么工具，而是遵循预设流水线。但它在“识图”环节引入了多模态 LLM（Qwen 视觉模型）进行图纸理解，具备 Agent 的“感知-推理-行动”特征。

### 1.5 为什么这个项目需要用 Agent，而不是普通应用？

核心原因是 **CAD 图纸是非结构化的视觉信息**，无法用传统规则解析全部内容：

| 挑战         | 传统应用局限                   | Agent 的价值                 |
| :----------- | :----------------------------- | :--------------------------- |
| 图纸布局多变 | 规则难以覆盖所有画法           | 多模态 LLM 视觉理解图纸内容  |
| 设计说明文本 | OCR 只能提取文字，无法理解语义 | LLM 解析材料规格、做法层次   |
| 图例符号识别 | 符号库无法穷举                 | 视觉模型识别符号并映射到构件 |
| 设计意图推理 | 规则无法推断“隐含信息”         | 假设-验证引擎推理算量边界    |

此外，该项目在 LLM 识别后叠加了 **确定性规则引擎**（算量、套价全部本地规则），实现了“LLM 理解图纸 + 规则计算数据”的混合架构——这是纯传统应用做不到的。

## 2. 业务流程

### 2.1 用户输入什么？

- **CAD 图纸文件**：DXF 或 DWG 格式
- **可选参数**：
  - `--steps`：指定执行哪些步骤（识图算量段或追加组价段）
  - `--specialty`：指定专业（房建/安装/市政/园林/钢结构）
  - `--render`：是否输出渲染图
  - `--keep-json`：是否保留中间 JSON
- **环境变量**：`QWEN_API_KEY`（阿里云百炼，用于视觉识别）

### 2.2 系统输出什么？

4 个 Excel 成果文件：

1. **图纸问题清单**：识图/审图阶段发现的问题
2. **工程量计算书**：详细计算过程
3. **分部分项工程量清单计价表**：无价格清单
4. **已组价清单**：含综合单价分析（仅组价段输出）

### 2.3 从用户输入到最终结果，中间经历了哪些步骤？

| 步骤         | 做了什么                                                     | 目的                                       | 涉及模块                                                     |
| :----------- | :----------------------------------------------------------- | :----------------------------------------- | :----------------------------------------------------------- |
| **① 识图**   | DXF→PNG 渲染 → Qwen 多模态视觉识别 → 几何解析 → 交叉验证；提取门窗表、文字标注、房间检测、图例解析、设计说明 | 将图纸转化为结构化数据（构件、尺寸、材料） | `step1_recognize.py`、`render_dxf.py`、`vision_query.py`、`vision_fusion.py`、`room_geometry.py`、`design_notes.py`、`legend_parser.py`、`intent_engine.py` |
| **② 审图**   | 24 条规则审查：编码格式/量纲/价格/必填字段/跨表一致/规范条文（GB 50010 等） | 发现图纸数据问题，防止错误进入算量         | `step2_review.py`                                            |
| **③ 算量**   | 构件级建模（24 类构件）× 5 专业计算器；构件扣减（板扣洞/墙扣门窗/梁柱重叠）；0 量占位卡口 | 计算各构件工程量                           | `step3_calculate.py`                                         |
| **④ 编清单** | 特征驱动套清单→国标清单匹配→自补清单（B 类编码）             | 生成符合国标的分部分项工程量清单           | `step4_compile_boq.py`                                       |
| **⑤ 组价**   | 多定额组合（土方=挖装+运土等）→定额价+主材价（真实价优先）→跨册借用/自补定额 | 生成含综合单价的已组价清单                 | `step5_price.py`                                             |

### 2.4 具体例子

**输入**：某住宅楼结构施工图 `住宅楼.dxf`，执行 `python pipeline.py 住宅楼.dxf --steps 识图,审图,算量,编清单,组价`

**流程**：

1. **识图**：渲染图纸为 PNG → Qwen 视觉模型识别柱、梁、板、墙位置和尺寸 → 几何解析提取轴线、标注 → 交叉验证（视觉置信度 0.85 ≥ 几何 0.72，视觉优先）→ 提取门窗表（C1 1800×2400 共 12 樘）→ 提取设计说明（C30 混凝土）
2. **审图**：检查 24 条规则——编码格式正确、量纲一致、跨表无冲突
3. **算量**：计算混凝土柱体积、梁体积、板面积、墙体体积；板扣洞（扣除楼梯洞口）、墙扣门窗（12 樘 C1 共 51.84m²）
4. **编清单**：生成清单项“现浇混凝土柱 C30”（编码 010502001）、“现浇混凝土梁 C30”等
5. **组价**：套辽宁 24 定额子目→查询主材价格库（C30 混凝土 420 元/m³）→计算综合单价

**输出**：4 个 Excel 文件，包含完整已组价工程量清单

## 3. 技术架构

### 3.1 前端、后端、Agent 服务分别用什么技术？

这是一个 **纯后端 CLI 工具**，无前端界面：

| 层次       | 技术                                |
| :--------- | :---------------------------------- |
| 运行环境   | Python 3                            |
| CAD 解析   | `ezdxf`（DXF 解析）                 |
| 视觉识别   | 阿里云百炼 Qwen 3.7-flash（多模态） |
| Excel 输出 | `openpyxl`                          |
| 图表渲染   | `matplotlib`                        |
| 调度编排   | 自定义 Pipeline（`pipeline.py`）    |

### 3.2 是否使用 LangChain、LangGraph 等技术？

**未使用**。该项目是**自研轻量级 Pipeline 框架**，没有依赖 LangChain/LangGraph 等编排框架。所有步骤调度、状态管理、数据传递均由自定义代码实现。

这说明项目采用了 **“够用即可”的工程哲学**——对于五步固定流水线，自定义编排比引入重型框架更可控、更轻量。

### 3.3 是否使用数据库或向量数据库？

**未使用**。所有数据以本地文件形式存储：

- 定额数据：`data/` 目录下的 JSON/CSV 文件（29,839 条）
- 清单数据：3,734 条
- 映射数据：1,847 条
- 主材价格库：268 条

无向量数据库，无 RAG 检索增强——因为定额/清单匹配是**确定性键值映射**（编码对齐），不需要语义检索。

## 4. Agent 核心设计

### 4.1 Agent 的角色是什么？

**造价工程师的自动化助手**——接收 CAD 图纸，自动完成“识图→审图→算量→编清单→组价”全流程，输出符合规范的工程量清单。

### 4.2 Agent 如何理解用户任务？

通过 **CLI 参数** 理解任务范围：

- `--steps 识图,审图,算量,编清单` → 只做算量段（无价格）
- `--steps 识图,审图,算量,编清单,组价` → 完整流程含组价
- `--specialty 市政工程` → 指定专业计算器
- 多张图纸输入 → 自动合并去重

### 4.3 Agent 是否会进行任务拆解或规划？

**是，但非 LLM 规划**。任务是**预定义的固定五步流水线**，由 `pipeline.py` 硬编码调度。这不是 LLM 动态规划，而是工程化的确定性工作流拆解。

但在“识图”环节内部，有**设计意图推理引擎**（`intent_engine.py`）进行假设-验证推理：

- 全局理解：工程性质、用途、概况
- 算量边界：含/不含项裁剪
- 参数推断：防水上翻高度、墙砖高度、踢脚等

### 4.4 Agent 如何决定是否调用工具？

**不是 LLM 决策，而是流水线阶段决定**。每个 step 执行时，按其职责调用相应工具：

- `step1_recognize` → 必然调用 `render_dxf` + `vision_query`（除非 `VISION_OFF=1`）
- `step3_calculate` → 必然调用各专业计算器
- `step5_price` → 必然查询定额库和主材价格库

这是一种 **“固定路由”而非“自主决策”** 的模式。

### 4.5 项目中有哪些 tools？

| Tool 名称      | 功能                               | 所在模块               |
| :------------- | :--------------------------------- | :--------------------- |
| DXF 渲染器     | DXF→PNG 图纸渲染                   | `render_dxf.py`        |
| 视觉识别器     | Qwen 多模态识别图纸内容            | `vision_query.py`      |
| 视觉融合器     | 视觉与几何交叉验证                 | `vision_fusion.py`     |
| 审图规则引擎   | 24 条规则批量审查                  | `step2_review.py`      |
| 构件计算器     | 24 类构件 × 5 专业算量             | `step3_calculate.py`   |
| 房间几何化     | 闭合区域→房间→实际分区量           | `room_geometry.py`     |
| 设计说明解析器 | 提取材料规格/做法层次              | `design_notes.py`      |
| 图例解析器     | 符号↔构件映射                      | `legend_parser.py`     |

### 4.6 是否使用 RAG、MCP 或 Skills？

| 技术       | 是否使用   | 说明                                                         |
| :--------- | :--------- | :----------------------------------------------------------- |
| **RAG**    | ❌ 未使用   | 定额/清单匹配是编码键值映射，非语义检索                      |
| **MCP**    | ❌ 未使用   | 无 Model Context Protocol                                    |
| **Skills** | ⚠️ 部分支持 | 项目根目录有 `SKILL.md`，描述了能力清单，但并非标准 Agent Skills 框架 |

### 4.7 Agent 如何生成最终结果？

**LLM 生成 + 规则生成混合**：

1. **LLM 生成部分**：视觉识别结果（Qwen 输出结构化 JSON）→ 经交叉验证后进入数据流
2. **规则生成部分**：算量（确定性计算器）→ 编清单（映射表匹配）→ 组价（定额库查询 + 价格库查询）→ Excel 输出

最终 **4 个 Excel 文件**由 `openpyxl` 生成，非 LLM 生成。

### 4.8 是否支持多轮对话、记忆或上下文管理？

**不支持**。这是一个**单次批处理 Pipeline**，无对话界面、无状态记忆、无上下文管理。每次执行是独立的，输入图纸 → 输出 Excel。

## 5. 工程化与可落地性

| 维度                 | 当前实现                                            | 不足                            | 改进建议                                |
| :------------------- | :-------------------------------------------------- | :------------------------------ | :-------------------------------------- |
| **异常处理**         | QC 断言 + 质量聚合报告                              | 无详细错误码、无重试机制        | 增加分级异常处理、视觉识别失败重试      |
| **日志和监控**       | 无明确日志框架                                      | 无结构化日志、无链路追踪        | 接入 `logging` + 关键步骤耗时埋点       |
| **权限控制**         | 无                                                  | CLI 工具无任何权限控制          | 如部署为服务，需增加 API Key + RBAC     |
| **工具调用安全**     | 本地文件读写 + 外部 API（Qwen）                     | 无输入校验、无 API 调用限流     | 增加文件大小限制、API 调用频率控制      |
| **RAG 没命中时处理** | 无 RAG；定额匹配是精确键值映射                      | 匹配失败时走“跨册借用/自补定额” | 可引入语义检索作为兜底                  |
| **扩展新工具/场景**  | 模块化设计，新增专业可加计算器                      | 无插件机制、无配置化注册        | 设计 Tool Registry + 配置文件驱动       |
| **数据合规**         | 明确标注数据含版权内容                              | 依赖辽宁定额数据，商用需授权    | 提供数据脱敏/替换方案                   |

| **测试覆盖**         | 单元 13/13、回归 8/8、构件 13/13、基准 20 用例 100% | 无集成测试、无 CI/CD            | 增加 CI 流水线自动化测试                |
| **视觉识别依赖**     | 强依赖阿里云 Qwen API                               | 无离线备选方案                  | 支持本地多模态模型（如 Qwen-VL 本地版） |

## 6. 总结与学习价值

### 6.1 核心亮点

1. **“LLM 理解 + 规则计算”的务实混合架构**：只在“理解图纸”这个非结构化问题上用 LLM，算量/套价等确定性计算全部用本地规则——既发挥了 LLM 的视觉理解能力，又保证了数据的可复现性和零幻觉。
2. **数据可信度卡口**：防“编造”——数字三要素校验、来源四级、待提取项不进清单。这是工程类 Agent 的关键设计。
3. **视觉优先交叉验证策略**：视觉置信度≥几何且≥0.7 时视觉优先，否则冲突标待核——不是简单二选一，而是置信度驱动的融合。
4. **两段式调用**：识图算量只出无价格清单，组价独立触发——符合真实业务场景（算量和组价常由不同人/不同阶段完成）。
5. **完备的内置数据**：29,839 条定额、3,734 条清单、1,847 条映射、268 条主材价格——让项目开箱即用。

### 6.2 不足

1. **不是真正的“自主 Agent”** ：它是固定流水线，没有 LLM 自主决策工具调用、任务规划的能力——更像“带 LLM 的自动化 Pipeline”而非 ReAct Agent。
2. **无多轮对话/交互能力**：CLI 批处理模式，用户无法在过程中纠正或干预。
3. **强依赖特定数据**：辽宁 24 定额 + 国标 24 清单，跨地区/跨版本适配成本高。
4. **无 Web 化/服务化**：本地 CLI 工具，难以集成到企业系统。

### 6.3 哪些设计值得学习？

1. **视觉与规则的双路融合**：LLM 负责“看懂”，规则负责“算准”——这是工程类 Agent 的最佳实践。
2. **数据可信度卡口**：在 LLM 输出进入下游前设置校验关卡，防止“幻觉污染”。
3. **两段式调用设计**：按业务阶段拆分能力，让用户按需调用。
4. **假设-验证推理引擎**（`intent_engine.py`）：用规则而非 LLM 做推理，保证确定性。
5. **多视图一致性校验**：平立剖跨图校验（面积/柱梁/层高/门窗 4 维）——领域知识工程化的好例子。

### 6.4 哪些设计不适合直接照搬？

1. **硬编码的五步流水线**：如果你的场景需要动态任务规划，这种固定 Pipeline 不够灵活。
2. **本地文件数据存储**：数据量增长后需迁移到数据库。
3. **特定地区的定额数据**：直接照搬无法适配其他地区/标准。
4. **无服务化设计**：企业级场景需要 API 封装，不能直接照搬 CLI 模式。

### 6.5 如果基于它二次开发，优先改哪些地方？

1. **封装 REST API**：将 Pipeline 封装为 HTTP 服务，支持异步任务提交和状态查询
2. **增加数据库层**：将定额/清单/价格库从 JSON 迁移到 SQLite/PostgreSQL
3. **设计插件机制**：支持自定义专业计算器、自定义审图规则的热插拔
4. **增加视觉识别兜底**：Qwen API 不可用时，降级到纯几何解析 + 规则推算
5. **容器化部署**：Docker 打包 + Kubernetes 部署支持

### 6.6 面试表达

> **项目背景**：CAD-BOQ Pipeline 是一个面向建筑工程造价领域的开源 Agent 项目，解决的是“CAD 图纸 → 工程量清单”全流程自动化问题。传统上这项工作由造价工程师人工完成，耗时长且易出错。
>
> **技术架构**：项目是纯 Python CLI 工具，核心依赖 `ezdxf` 做 CAD 解析、阿里云 Qwen 3.7-flash 做多模态视觉识别、`openpyxl` 输出 Excel。没有使用 LangChain/LangGraph 等编排框架，而是自研轻量级五步 Pipeline 调度器。
>
> **Agent 工作流**：采用固定五步流水线——识图（视觉+几何双路融合）→ 审图（24 条规则）→ 算量（24 类构件 × 5 专业计算器）→ 编清单（特征驱动套清单+自补清单）→ 组价（多定额组合+主材价格库）。视觉识别采用“置信度优先”策略：视觉置信度≥几何且≥0.7 时视觉优先，否则标待核。
>
> **Tools / RAG / MCP / Skills**：项目未使用 RAG（定额匹配是编码键值映射而非语义检索），未使用 MCP。Tools 是确定性函数（渲染器、计算器、规则引擎、映射表查询），而非 LLM Function Calling。根目录有 `SKILL.md` 描述能力清单，但非标准 Agent Skills 框架。
>
> **项目亮点**：一是“LLM 理解 + 规则计算”的混合架构——只在图纸理解环节用 LLM，算量套价全部本地规则，保证零幻觉和可复现；二是数据可信度卡口，防止 LLM 编造数据进入清单；三是两段式调用设计，算量和组价可独立触发，贴合真实业务场景。
>
> **企业级落地思考**：当前是本地 CLI 工具，企业级落地需要封装 REST API、增加数据库层、设计插件机制支持自定义专业和规则、容器化部署，以及增加视觉识别失败的降级兜底方案。
